# REST

Один адрес приложения принимает все намерения порта навигации. Запрос
называет намерение и его данные, ответ — то, что порт вернёт компоненту.

## Перед началом

- Порт на странице — [Сервер](../).
- Сессия администратора и защита от подделки запроса (CSRF-токен), которые
  уже есть в приложении.

## Шаги

1. Примите запрос:

   ```http
   POST /admin/navigation
   Content-Type: application/json

   {"intent": "favourite.toggle", "payload": {"key": "srv.dns"}, "page": "/admin/dns"}
   ```

2. Проверьте права человека на это намерение. Нельзя — ответьте `refused`
   с причиной, которую можно показать:

   ```json
   {"answer": "refused", "reason": "Избранное недоступно для этой роли."}
   ```

3. Сделайте дело и ответьте `applied` с данными намерения. Для
   `navigation.load` — дерево меню, текущую строку и человека; для
   `favourite.toggle` — новое избранное:

   ```json
   {"answer": "applied", "favourites": [{"key": "srv.dns", "label": "DNS-зоны", "href": "/admin/dns"}]}
   ```

4. Если меню успело измениться с тех пор, как его прочли (другой
   администратор сохранил профиль меню), ответьте `conflict` с новой
   ревизией и данными — меню покажет их человеку.

5. Сервер не смог ответить (база недоступна) — `unavailable`. Порт на
   странице отвечает так же, если запрос не дошёл.

## Ответы на уведомления

`notifications.load` отвечает днями с уведомлениями внутри:

```json
{
  "answer": "applied",
  "unread": 2,
  "settings_href": "/admin/notifications/settings",
  "next_cursor": null,
  "groups": [
    {"key": "today", "label": "Сегодня", "items": [
      {"key": "n1", "title": "srv1 не отвечает", "when": "10:42", "unread": true, "href": "/admin/servers/srv1"}
    ]}
  ]
}
```

`notifications.read` приходит с `{keys, all}` и отвечает новым числом
непрочитанных: `{"answer": "applied", "unread": 0}`.

## Результат

Один маршрут отвечает и меню, и уведомлениям, а права проверяются на
сервере для каждого намерения — то, чего человеку нельзя, не дойдёт до
данных, даже если управление нарисовано.
